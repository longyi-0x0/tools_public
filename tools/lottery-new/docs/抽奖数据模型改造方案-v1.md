## 一、已确认的产品决策（用户口径）

| 编号 | 决策 | 对设计的约束 |
| --- | --- | --- |
| D1 | 不绑定任何一种抽奖方式；数据底座统一，表演形式由 `form` 覆盖 | 模型里禁止出现「转盘专用字段」「九宫格专用字段」 |
| D2 | 是否"抽运气"由**池的内容**自然决定：有「谢谢参与」这类条目就是抽运气，没有就是抽一个少一个 | 不引入「业务类型」开关；它是数据涌现出来的结果 |
| D3 | 池可以分组，也可以不分组；用分组补上「活动 / 环节」这一层 | 分组必须是**可选**的，不分组时功能不降级 |
| D4 | 目标是把一次抽奖带走：云同步，或导出 | 导出与同步都要选型，且要定义往返口径 |
| D5 | 适用人群从小学生课堂到公司年会 | 默认路径必须零配置；所有高级概念默认折叠 |

**从 D5 推出一条硬原则**：任何概念如果不能对小学生（老师点名）和年会主办（全场限中一次）同时成立，它就必须被做成「可选的高级项」，而不是默认参数。这条原则是下面所有取舍的依据。

## 二、业界做法参考（检索于 2026-10-22）

> 说明：以下为公开仓库 README / 文档 / 代码结构层面**可查证的做法**，不是市场调研数据，也不代表用户调研结论。引用只用于理解通用建模思路。

| 项目 | 数据抓手 | 对本文的启示 |
| --- | --- | --- |
| log-lottery（LOG1997） | `prizeList`：奖项含「抽取人数 count」「是否全员参与 isAll」；`allPersonList` 名单；`alreadyPersonList` **结果按奖项分组**；`currentPrize` 当前奖；持久化 IndexedDB + localStorage | 奖项自带名额与参与范围；结果天然挂在奖项下 |
| Magpie-LuckyDraw | 「获奖者不重复中奖」「奖项抽取出场顺序」「灾难恢复：意外退出可恢复上次抽奖」 | 去重是默认；**出场顺序**是一等配置；现场工具要兜中途崩溃 |
| lucky-draw（vitozyf） | 名单 + 奖项（含 count）；抽中即从候选移除；结果可追溯 | 「抽中即消耗」是最朴素也最常被期待的默认 |
| lucky（scavin） | CSV 列：`姓名,部门,必中奖项,禁止中奖,权重(1-10)` | **排除（黑名单）/ 必中 / 权重** 是参与人属性，业界标配三件套 |
| github-raffle | `Prize{id,name,amount}`、`Winner{user,prize}`；已中奖者自动从候选剔除 | 结果与奖项绑定；全局去重由 winners 派生 |
| lotery-drawer | `tickets{参与者: 票数}`；奖品 `{name, nb}`；票中了就从票池移除 | 「票」是本模型里 `weight` 的另一种写法，不必单独引入 |
| ORaffle | 结果带名次 ranking；支持导出/分享 | 结果要有次序，便于沉淀成记录 |

**收敛结论（参考观点）**：业界没有强制标准，但**所有做法都收敛在同一处**——

```text
奖项（带名额）  +  参与人（带 排除 / 必中 / 权重 属性）  +  结果（带奖项归属与次序）
```

三条共性事实：(1) 抽中即去重是默认行为；(2) 名单/结果的 xlsx 导入导出是标配；(3) 整份配置导出再导入，是单机工具「数据带走」的主流做法。

**我们的差距**：这三条里，我们只有 (2) 的一半（能导出结果 xlsx），而最关键的第 (1) 条**作用域没定义**——这正是第三节要解决的。

## 三、问题重述：真正缺的是什么

用户提的三个现象，落到模型上其实是四个缺口：

| 现象（用户原话） | 真实缺口 | 现有机制为什么兜不住 |
| --- | --- | --- |
| 「谢谢参与需要放回，其他不需要放回」 | **条目有没有"永不耗尽"的表达** | `Entry.stock` 语义正确，但 UI 只能输正整数，无法表达 ∞ |
| 同上 | **"不要重复抽到"的范围** | `Rule.replacement` 只管**同一轮内**能否重复，`pickLimit` 只限次数，二者都没说清"跨场次/跨环节"怎么办 |
| 「缺活动 / 环节这一层」 | **结果的归属链断了** | `Round.drawId` 在 `engine.js` 里写进去了，UI 层一次都没读过；`ledger.usageIn` 只按 `poolId` 算，"名额是否跨抽奖共享"从未定义 |
| 「目标是云同步或导出」 | **没有完整的工程载体** | 只能导出结果 xlsx，池与抽奖配置带不走 |

**判断**：这四个缺口里，只有第 1 个是"加个字段"，其余三个都是**语义要重新定义**。所以不能只做最小改动。

## 四、方案对比

| 方案 | 思路 | 实现成本 | 复杂度 | 体验 | 风险 | 综合评价 |
| --- | --- | --- | --- | --- | --- | --- |
| **A. 只补 `stock = ∞`** | 给文案式的不限量开个口子，"谢谢参与"就配 ∞ | 低 | 低 | 中 | 低 | 能解"谢谢参与"，但对 D3（活动层）毫无帮助，跨场次的限中仍做不到 |
| **B. 抽出「消耗作用域 scope」（推荐）** | 保留开销要件的同时，把"在多大的范围内不重复"抽成一等字段；配合 `stock = ∞` 表达"谢谢参与" | 中 | 中 | 好 | 低 | 一次改动同时闭环 D2 与 D3，且不破坏"池 + 抽奖"两层结构 |
| **C. 引入三层实体（活动 / 奖项 / 名单）** | 照搬年会类工具的经典三层 | 高 | 高 | 中 | 中 | 与 D1/D5 冲突：小学生点个名也要先建"活动"，强加心智负担；且会把"表演形式"也一起绑进这三层，与 D1 直接冲突 |

**推荐方案 B**，理由：

1. **它把 D2 变成了数据的副产品**——池里放「谢谢参与」且 `stock = ∞`，自然就是抽运气；全是消耗型条目，自然就是抽完少一个。不需要开关，符合用户直觉。
2. **它用 D3 的"分组"做作用域的边界**——分组只承担"哪些抽奖算同一场"，逻辑仍然由 `Draw` 自己表达，所以不分组时不影响任何语义，满足"可以分组也可以不分组"。
3. **它是加法不是重写**——`pool / draw / round / ledger` 四件套不动，`engine` 的抽取算法只需多接一个入参。

不推荐 C：它年会味太重。用户明确说过适用人群下到小学生，一旦强三层，最轻的场景就被迫承受最重的模型。

## 五、推荐方案：stock + scope

### 5.1 模型改动（before → after）

```text
【现】
Entry { id, label, weight = 1, stock = 1, tags: [], meta: {} }
Rule  { count, replacement, weighted, pickLimit, hitRate }
Round { id, drawId, seed, ... }            ← drawId 写了但没人用

【改】
Entry { id, label, weight = 1, stock = 1 | ∞, exclude = false }
Rule  { count, scope: 'draw' | 'group' | 'always', weighted, pickLimit }
Draw  { id, name, groupId = null, slots, form, mode, rule }
Group { id, name }                          ← 可选；不分组则 groupId 为 null
Round { id, drawId, seed, picks, sample, at, win, status }
```

### 5.2 字段口径表

| 字段 | 层级 | 口径 | 缺省 | 备注 |
| --- | --- | --- | --- | --- |
| `stock` | Entry | 这个条目能被抽中的总数；抽完即从候选消失 | `1` | **新增取值 `∞`**，用于「谢谢参与」这类不消耗的占位条目。存货由账本派生，不自存计数（沿用现有不变量 1） |
| `exclude` | Entry | 是否排除出候选（黑名单/候补） | `false` | 业界标配（scavin/lucky 的"禁止中奖"列）。抽 `exclude` 为真的条目不再进候选，但历史结果里仍能显示名字 |
| `weight` | Entry | 相对权重 | `1` | 保留不变；`weighted = false` 时忽略 |
| `scope` | Rule | **同一个人能不能再被抽中**的作用域 | `'draw'` | 取代原 `replacement`。三档见 5.3 |
| `pickLimit` | Rule | 单条目在这个抽奖里最多被抽中几次 | `∞` | 与 `stock` 取小。0 或空 = 不限 |
| `count` | Rule | 一次抽几个 | `1` | 保留不变 |
| `groupId` | Draw | 归属哪一场活动（可为空） | `null` | 只做组织与作用域边界，**不参与抽取逻辑** |
| `drawId` | Round | 结果归属哪个抽奖 | 必填 | **UI 层必须开始用它**（当前完全没用） |

### 5.3 `scope` 三档（替代 `replacement`）

| 取值 | 界面文案 | 语义 | 典型场景 |
| --- | --- | --- | --- |
| `draw` | 本轮不重复 | 只在**这一次抽奖**里同一个人不会被重复抽中；换一场抽奖他还能中 | 默认值；老师随机点名、`count = 5` 一次抽 5 个不同的人 |
| `group` | 同一场活动不重复 | 该 Draw 需挂在某个 Group 下；同一 Group 内所有 Draw 共享已中名单 | **年会：全场每人限中一次**（三等奖再到一等奖不会重复同一个人） |
| `always` | 一直不重复 | 这台机器上任何时候都不再抽中他 | 客户名单、已抽过的 old 名单；谨慎使用 |

配套规则（可测）：

- `scope = 'group'` 而 `groupId` 为空时：UI 必须提示并阻止保存，不允许静默退化成 `draw`。
- 「谢谢参与」类条目 `stock = ∞`，因此它在任何 scope 下都不会被消耗——**这就是用户要的"谢谢参与放回、其他不放回"**，不需要额外的放回开关。
- 改名不留兼容层：**字段改名不改语义**，`replacement` 取消后不留别名与兼容分支（见 AGENTS.md 规则 3）。

### 5.4 "抽运气"为什么不需要开关

用户说得很准：业务性质是池的内容决定的。验证一下这套模型能否覆盖——

| 场景 | 池内容 | 结果 |
| --- | --- | --- |
| 老师随机点名答题 | 全为学生，`stock = 1` | `scope = draw`，一轮内不重复；下一轮所有人回到池里 |
| 年会三等奖抽 20 人 | 全员名单，`scope = group` | 抽到的人在其他奖项里不会再出现 |
| 转盘抽奖品 | 「谢谢参与 ∞ + 一等奖 1 + 二等奖 3」 | 谢谢参与永不耗尽 → 抽运气；奖品抽完即空 → 抽消耗；同一池混着配也没问题 |
| 抽签决定是否补课 | 「是 ∞」「否 ∞」 | 两个都是 ∞ 的占位条目，纯概率游戏 |

结论：**四个场景都由数据自然成立，模型里没有一个"业务类型"字段**。这就是干净的证据。

### 5.5 Group 的定位：组织层，不是逻辑层

- **它是可选的**：不分组时 `groupId = null`，所有功能照常，只是 `scope = 'group'` 不可用。
- **它承担三件事**：① 侧栏把同一场活动的抽奖归在一起；② 作为 `scope = 'group'` 的边界；③ 批量操作单元（导出这一场、重置这一场的中奖记录）。
- **它不承担抽取逻辑**：`Group` 里没有字段参与 `decide()`。这条保证"不分组也能用"。

## 六、导出与云同步

### 6.1 选型对比

| 载体 | 能带走什么 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **xlsx（多 sheet）** | 池 / 抽奖 / 结果都能扁平化塞进去 | 人类可读，财务与行政能直接用 | 可随意编辑，往返不可靠；无法表达 ∞ 与嵌套；缺列就丢语义 | **只做输入与交付物**（导入名单、导出中奖名单给人签字），不做工程备份 |
| **JSON 工程文件** | 池 + 抽奖 + 结果 + seed 全量 | 往返无损；一个文件就是一次活动的完整快照 | 不可读，需要 UI 承载 | **主载体**：导出/导入整份工程 |
| **云同步** | 多设备实时 | 解决换机器、多人协作 | 涉及真实个人信息；需要账号与权限 | **后续版本**，且要过合规（见 6.3） |

### 6.2 推荐：JSON 为主、xlsx 为辅、云同步后置

- **V1**：「导出工程 / 导入工程」按钮，产出 `抽奖-<活动名>-<日期>.json`，含 `{ pools, draws, rounds, groups, exportedAt, schemaVersion }`。
- **导出时机也要给**：每场活动结束导出一次，习惯由 UI 句式提示，不能指望用户记得。
- **xlsx 保留两条**：① 名单导入（现已有 `importXlsx`，需一起修掉"表头当条目""只读第一列"）；② 中奖记录导出。
- **云同步走现有能力**：仓库已有 `caps/` 里的云能力包与 `tool.json` 的 `capabilities` 通道，不必自造通道——但同步前必须完成 6.3 的合规项。

### 6.3 数据合规要点（一旦涉及名单上云就必须完成）

名单是**真实个人信息**（姓名、部门、工号），上云前至少要有：

| 项 | 要求 |
| --- | --- |
| 告知同意 | 首次同步前明示：哪些数据会离开本机、存在哪里、谁可见 |
| 最小必要 | 只同步抽奖必需的字段；不外传用于其他目的 |
| 不强制 | 不启用云同步也可完整使用，功能不降级 |
| 可删除 | 提供「删除云端数据」入口，且删除后本地不受影响 |
| 传输与存储 | 传输加密；存储位置与保留期限明示 |
| 未成年人 | 若名单含未成年人（小学/班级场景），默认禁止上云，除非有学校/监护人明确授权 |
| 导出即是留痕 | 导出文件同样属于个人信息载体，UI 需提示"这个文件包含名单" |

> 本方案为产品设计参考，具体实施请结合公司合规与法务要求确认。

## 七、MVP 切分与版本规划

| 版本 | 内容 | 目标验收 |
| --- | --- | --- |
| **V1 数据底座** | `stock = ∞`、`scope` 取代 `replacement`、`exclude`、`Group`（可选）、UI 真正按 `drawId` 读记录 | 四个典型场景（点名 / 年会限中 / 谢谢参与 / 抽签）都能在不改代码的前提下配出来 |
| **V2 数据带走** | 工程 JSON 导出导入；xlsx 导入修好（跳过表头、支持 名字/权重/份数 三列）；中奖记录导出带上场次名 | 换电脑、清缓存后能完整恢复；一份文件能交给另一个人接着用 |
| **V3（后续）** | 云同步；灾难恢复（意外刷新回到上次未结算状态）；按 Group 批量重置 | 现场可靠性 |
| **本期不做** | 账号体系、多人协作、抽奖流程审批、国际化 | 记入后续版本池，防止范围蔓延 |

**依赖评估**

| 依赖项 | 所属 | 就绪状态 | 分级 | 影响与替代 |
| --- | --- | --- | --- | --- |
| 云能力（`caps/` 的 kv / docs） | 本仓 + toolbox_service | 已存在但未在 lottery-new 启用 | 并行 | 缺失时降级为"仅本机 + JSON 导出"，不影响 V1/V2 上线 |
| `importXlsx` 修复 | 本工具 | 未做 | 并行 | 缺失时用户只能手工录入名单，体验降级但不阻塞 |

## 十、附录：一句话总结

> `stock = ∞` 表达"谢谢参与"，`scope` 表达"在多大的范围内不重复"，`Group` 可选地提供那个范围；业务性质不设开关，让它从池的内容里自己长出来。数据带走先做 JSON 工程文件，xlsx 留给名单与结果，云同步后置并先过合规。
