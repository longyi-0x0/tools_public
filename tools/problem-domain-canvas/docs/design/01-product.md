# 问题域画板 · 产品设计 v2

## §1 一句话定位 + 核心体验

一句话：一个**两域画板**——先在「问题域」把模糊问题推成清晰的问题结构，拨一下切到「解域」把结构推成领域模型（实体、行为、约束）。它不是思维导图，也不是自由画板。

核心体验（沿用 v1，把解域接上）：

> 用户始终知道**我在答什么问题、它还缺什么、下一步澄清什么**；切到解域后还知道**这个实体在支撑哪个问题**。

四处落点，缺一处就算没做到：

- 我在答什么问题：顶栏「工作区名 + 一行目标」；选中节点的标题。
- 它还缺什么：右栏检查区（§5），常驻可见、不折叠成抽屉。
- 下一步澄清什么：问题树里状态为「未澄清」的问题顶在最前，每行一句「建议先澄清」。
- 它支撑哪个问题：解域里选中实体/行为/约束，右栏第一行就是「支撑：P1 选课资格如何判定」，可点回跳（§6）。

## §2 两个域是什么、边界在哪、为什么这么切

- 问题域只谈**要解决什么**：有哪些问题、谁参与、在什么场景、涉及哪些概念/规则/事件、还缺什么信息。**这个域里没有任何实体/关系/行为/约束的编辑入口。**
- 解域才谈**怎么解**：实体（对象、字段、状态）、行为（实体上能做什么）、约束（必须满足什么）。
- 两个域共享**同一份工作区文档**：一份 JSON，切换只换渲染面与可编辑面，不换数据、不产生两份真相。
- 为什么这么切：v1 把领域模型塞进问题域，8 类节点、15 条边、5 个视图挤在一屏，人要同时想「这算不算问题」和「这要怎么实现」。切开后每一屏只回答一个问题域内的问题。

同一个概念在两个域里的两种身份（选课样例）：

- 「选课资格」在问题域 = 一个 `question`，还没答清：容量、先修、时间冲突谁优先。
- 「选课资格」在解域 = `entity: 选课记录` 上的一个 `behavior: 提交选课`，外加 `constraint: 已选人数 < 容量`。
- 「学生」在问题域 = `actor`（参与者，只描述它怎么参与）；在解域 = `entity`（才有 `data.fields`、才有主键）。

## §3 两列版式与 2 个视图

整页只有两列，没有全局顶栏：

- 左列（240–280，占满页高）：顶部一行 = 「领域」小标签 + 弹性留白 + 紧凑的 `问题域│解域` 分段切换；下面是树，占满剩余高度、可滚、不可收起。**两域的树不同**：问题域 = 问题树（P0 → P1 → P1.1 / P1.2；P2，每行 = 缩进 · 标题 · 状态）；解域 = 「实体 · 关系」两段扁平列表（实体行 = 名称 + 类型点 + 支撑徽标，未支撑只在行尾给一个红点；关系行 = `A —持有→ B · 1:N`）。字段 / 行为 / 约束 / 支撑关系不进左树，只在右列详情里。
- 右列（弹性）：顶部信息行（44，无背景、无圆角、无阴影）= 当前选中标题 + 父级路径（左）· 已保存三态 + 导出 / 撤销 / 重做 / 主题切换（右）；检查摘要在左树底部（高 36），缩放四件在画板右上角的悬浮工具条（高 30）；下方内容 = 画板（弹性，可收起）+ 详情（340，可收起）。
- 每域只有一个画板（问题域 = 问题树画布；解域 = 领域模型画布），导航由域切换承担，**不放视图 tab**；换域不改数据、不丢选中。
- 目标仍是核心问题的一句话，展示在顶部状态左侧；改这里等于改 `workspace.goal`。

### 3.1 问题域 · 问题树（默认）

- 显示：核心问题为根、`decomposesTo` 成树；每行「状态点 · 标题 · 缺失项角标」；无父的问题单独一组「未挂到核心问题上」。
- 能做：新建/改名/删问题（删问题连带删边）；拖拽建 `decomposesTo`；点行进详情。（`dependsOn` 入口见 §7 表末行「建立依赖…」。）
- 空状态：`还没有核心问题` + 说明 `先写一句「要解决什么」，再往下拆。` + 主按钮 `＋ 新建核心问题` + 次按钮 `导入 JSON`。

### 3.2 右栏面板 · 详情与检查（不再是视图）

- 「问题详情」由独立视图降为右栏「详情与检查」面板的内容态：未选中时右栏显示工作区概览（工作区名 / 目标 / 范围内外 / 检查摘要），选中问题时显示该问题详情。两域共用这一块右栏，所以视图数从 3 个降到 2 个。
- 显示：陈述、目标、边界、已知、假设、正例/反例文本、答案形式、判定标准、状态、关联（参与者/场景/概念/规则/事件）、检查命中、**解域支撑（只读列表，可跳）**。
- 能做：改所有字段；5 态流转；挂关联边；把一条假设一键转成待澄清问题。
- 空状态：`左边选一个问题看详情。`

### 3.3 解域 · 领域模型（默认）

- 显示：实体方框（字段与 `states` 列在框内）、`entityRelation` 连边标基数（1:1 / 1:N / N:M）、行为与约束作为小标签挂在实体上；每个元素右上角有「支撑 P?」徽标，未支撑标红。
- 能做：新建/改/删实体、行为、约束；连 `entityRelation`；给任意元素挂 `supportsQuestion`；点徽标跳回问题详情。
- 空状态：`还没有实体` + 说明 `解域是空的。先从问题树挑一个已回答的问题，再建它的第一个实体。` + 主按钮 `＋ 新建第一个实体`。

## §4 数据模型

### 4.1 工作区与统一信封

```json
{
  "schemaVersion": 2,
  "name": "选课问题域",
  "goal": "如何正确处理选课？",
  "coreQuestionId": "q0",
  "nodes": [],
  "edges": []
}
```

9 类节点共用一个信封：

```json
{ "id": "q1", "type": "question", "title": "…", "notes": "", "data": {}, "pos": { "x": 0, "y": 0 } }
```

`type` 枚举：`question | actor | scene | concept | rule | event | entity | behavior | constraint`。`notes` 任意类型可用（原 `note` 节点降级于此）。

### 4.2 各类型 `data` 字段

| 域 | type | data 字段 |
| --- | --- | --- |
| 问题 | `question` | `status`（未澄清/分析中/已澄清/已回答/暂缓）、`statement`、`goal`、`boundary`、`knowns[]`、`assumptions[]`、`positiveCases[]`、`negativeCases[]`、`answerForm`、`criteria[]` |
| 问题 | `actor` | `role`、`description` |
| 问题 | `scene` | `trigger`、`steps[]` |
| 问题 | `concept` | `definition`、`aliases[]` |
| 问题 | `rule` | `statement`、`source` |
| 问题 | `event` | `trigger`、`effect` |
| 解 | `entity` | `identity`（主键名）、`fields[{name,type,required,note}]`、`states[]`（字符串数组，不是节点） |
| 解 | `behavior` | `inputs[]`、`output`、`preconditions[]`、`effects[]` |
| 解 | `constraint` | `expr`、`kind`（必须/禁止）、`enforcementPoint` |

问题状态 5 个：未澄清 → 分析中 → 已澄清 → 已回答；任一步可置「暂缓」（带 `deferReason`）。状态只影响排序与提示，**不阻断任何编辑或导出**。

### 4.3 关系 11 条（不再扩）

| 域 | 类型 | source → target | 语义 |
| --- | --- | --- | --- |
| 问题 | `decomposesTo` | question → question | 父问题拆出子问题 |
| 问题 | `dependsOn` | question → question | 答 B 之前要先答 A |
| 问题 | `involvesActor` | question → actor | 这个问题涉及谁 |
| 问题 | `occursInScene` | question → scene | 问题发生在什么场景 |
| 问题 | `concernsConcept` | question → concept | 问题绕不开的概念 |
| 问题 | `constrainedByRule` | question → rule | 问题被哪条规则约束 |
| 问题 | `triggeredByEvent` | question → event | 问题由什么事件引发 |
| 解 | `entityRelation` | entity → entity | 实体间关系（边上带基数） |
| 解 | `behaviorOnEntity` | behavior → entity | 这个行为作用在哪个实体 |
| 解 | `constraintOnEntity` | constraint → entity | 这条约束守哪个实体 |
| 解 | `supportsQuestion` | entity \| behavior \| constraint → question | **它支撑哪个问题**（§6 的支点） |

跨域只有 `supportsQuestion` 一条，方向恒为「解 → 问题」。

`entityRelation` 支持可选 `label`（关系名，如「持有」）：只给这条边用，不新增边类型、不改基数语义。

## §5 检查 6 条

全部**不阻断**：最高级别只到「错误」，红点照样能编辑、能导出。每条一句话给文案与点击去处。

| # | 什么时候报 | 提示文案 | 点了去哪 |
| --- | --- | --- | --- |
| C1 | `coreQuestionId` 为空，或核心问题没有任何 `decomposesTo` 出边（错误） | 「核心问题还没写 / 还没拆成子问题」 | 空则聚焦新建框；有则选中核心问题，看它的子问题列表 |
| C2 | 除核心问题外，某问题既无任何问题间边（`decomposesTo`/`dependsOn`）也为零入边（错误） | 「这个问题跟别的问题都没关系」 | 选中该问题，问题树里该行常亮，右侧给「挂到问题树 / 加依赖」两个按钮 |
| C3 | `decomposesTo` 子图成环（错误） | 「分解成环了：A → B → A」 | 高亮环上全部节点与边，阻断只在这条路上新建 `decomposesTo`（提示不锁定其它编辑） |
| C4 | 问题状态为「已回答」但正例或反例至少一边为空（错误） | 「已回答，但没有例子」 | 选中该问题、滚到「正例/反例」两栏 |
| C5 | 状态为「未澄清」或存在未处理假设（错误级别提示），含 `rule` 被 `constrainedByRule` 引用但节点已不存在 | 「还有 N 条假设 / 待澄清没处理」或「引用了不存在的规则」 | 选中对应问题并展开「假设」；规则缺失则跳到该边与两端节点 |
| C6 | 解域中某 `entity`/`behavior`/`constraint` 没有 `supportsQuestion` 出边（错误） | 「这个实体不支撑任何问题，先回答它为什么存在」 | 切到解域并选中该元素，右栏顶部给「选择它支撑的问题」下拉 |

## §6 两个域怎么衔接

1. **支撑关系**：解域每个元素必须回答「它支撑哪个问题」。新建实体/行为/约束时，保存前给一次下拉选择（可跳过，但会立刻命中 C6）。
2. **回跳**：解域元素卡片上的「支撑 P?」徽标、右栏第一行，两处都能一键跳到该问题的详情视图（切域 + 选中 + 展开关联段）。
3. **正向透光**：问题详情里有一节「解域支撑」，只读列出支撑它的实体/行为/约束，点一下反向跳到解域。
4. **孤儿检测**：C6 是这条约束的唯一执行者；领域模型里未支撑的元素带红色徽标，随时可数。

这就是本产品与思维导图的分界：思维导图里两张图各画各的；这里解域的每一个框都要能指回一个还没答完的问题，指不回去就被点名。

## §7 创建与编辑

五种入口各有唯一语义，互不重叠；任何入口最多一次行内输入，不弹第二步对话框（「建立依赖…」是唯一的建边入口，不改节点）。

| 入口 | 语义 | 落成什么 |
| --- | --- | --- |
| 树段头 `＋` | 「给这一段加一条平级」 | 问题域：加一个无父问题（进「未挂到核心问题上」组，§3.1），不建任何边；解域：「实体 · 关系」两段的段头分别只建实体、只建关系 |
| 行内 `＋` | 问题行「加子问题」/ 实体行「加同级实体」 | 问题行 `＋` = 新建子问题并自动建 `decomposesTo`（父 = 该行）；实体行 `＋` = 新建同级实体（行为与约束在右栏详情里建，不在树上建） |
| 画布空白双击 | 「在这儿放一个框」 | 问题域建 `question`、解域建 `entity`，`pos` = 双击点；不自动建边、不改 `coreQuestionId`；双击已有节点 = 进详情改名 |
| 空态主按钮 | 「一步把工作区开起来」 | 空工作区：建核心问题并写入 `coreQuestionId`；解域空态：建第一个实体，同一步里给一次支撑问题下拉（可跳过，跳过即命中 C6，与 §6 一致） |
| 建立依赖… | 问题行 `⋯` 菜单「建立依赖…」（位置：`新建子问题` 之后、`重命名` 之前）「先答 A 才能答 B」 | `dependsOn` 边（画布上虚线）：进入选目标模式，底部引导条 `已选起点：P1 选课资格 · 点另一个问题完成 · Esc 取消`；点自己 / 重复边 / 非问题节点被拒；一次操作一条撤销记录（§7.4）；`Esc` 取消不留边；建成的依赖在左树问题行尾给 `↗` 角标（`title` 写「有 N 条依赖」） |

### 7.1 最小必填与「未命名」中间态

**通用**：新建只需入口已定的 `type` + 自动 `id` + `pos`；`title` 允许为空，进入「未命名」。按类型的结构性必填只有三处：`rule` 必须给 `data.statement`（没陈述的规则会在 `constrainedByRule` 处制造假引用）、`constraint` 必须给 `data.expr`（没表达式既不能校验也进不了 §8 的注释）、`entity` 必须给 `data.identity`（`behaviorOnEntity`/`constraintOnEntity` 与导出都靠它）。其余 6 类没有结构性必填——靠 §5 检查兜底，不靠表单挡人。`behavior` 另有一条结构要求：`behaviorOnEntity` 的 target 在建时就要定（在右栏详情新建时带，画布双击后补一次下拉）。

「未命名」的存活规则（结论三条）：

1. 只活一个编辑会话：从新建到「失焦 / 切域 / 刷新」三者先到的那一下；到点仍空 → 丢弃，不写盘、不进检查、不进导出，不留空壳。
2. 同一时刻最多 1 个未命名节点；再点任意入口时先把上一个落库，落库时空标题写成「未命名」。不允许并存两个空标题节点。
3. 未命名节点不能被引用：不能当任何边的端点、不进树排序——否则会死在图里，删不掉也连不上。

### 7.2 派生：新建子问题继承什么

只继承一样：父问题的 `data.boundary`（范围）原样复制。理由：子问题的范围几乎总是父范围的裁剪，重写只减信息，写歪就变成两套边界。

不继承、留空并给提示的：`goal`（子问题目标不同）、`knowns[]`/`assumptions[]`/`positiveCases[]`/`negativeCases[]`/`criteria[]`（父的证据不能替子问题作证）、`status` 重置为「未澄清」（父已澄清不等于子已澄清）。

关联边（`involvesActor`/`occursInScene`/`concernsConcept`/`constrainedByRule`/`triggeredByEvent`）**不复制**，但新问题详情顶部给一行「父问题还关联了：学生、选课场景、不得超容量 —— [全部沿用]」。理由：复制等于替用户断言「子问题也一样涉及」，而参与者通常是父集合的真子集；沿用是一次点击，代价远低于事后清理错边。

### 7.3 关系怎么建（结论）

**先选元素，再从元素建边**，不做「先建边再选元素」。

- 解域 `entityRelation`：选中两个实体才能建（选第一个后点「连关系」，再点第二个）；只选一个时不给入口。
- 问题域关联边：在问题详情里挂。选中问题后可建的 6 条边里 target 类型都是确定的，界面只需问「哪个参与者 / 哪条规则 / 哪个场景」。
- 理由：11 条边每条都固定了 source/target 类型，用户脑子里的对象是「这个参与者和这个问题」，不是「第 4 条边叫什么」。先建边就得先让人从 11 个名字里挑一条，再回头找两端——两次都不在他当前上下文里。拖拽建 `decomposesTo`/`entityRelation` 不算另一种语义，它就是「先选两端」的鼠标姿势。

### 7.4 删除与撤销

- 删问题：删掉它的全部出入边（`decomposesTo`/`dependsOn`/5 类关联边/指向它的 `supportsQuestion`）。**子问题不删**，脱挂进「未挂到核心问题上」组由 C2 点名。删的是核心问题时 `coreQuestionId` 置空，C1 立刻报错但不阻断（符合 §5）。
- 删实体：级联删除它身上的 `entityRelation` 与 `behaviorOnEntity`/`constraintOnEntity` 边，以及挂在它上面的 `behavior`/`constraint`（不再由 C6 点名）；整步可撤销（行为与约束一起回来），删除确认里写明「N 个行为、M 条约束将一并删除」。
- 删其余 6 类节点（`actor`/`scene`/`concept`/`rule`/`event`）：删节点即删其全部关联边，不连带任何节点。
- 撤销：一次删除算一步（连带边一起回来），会话内内存保留最近 10 步，刷新即失；导出/导入、重命名不进撤销栈。

### 7.5 重命名与合并（结论）

v1 的「同概念多名」检查已按 §9 砍掉，**不恢复**；用「合并」替代，且只在 `concept` 与 `entity` 两类上给。

- 入口：详情里「合并到…」→ 选同类节点 → 预览「4 条边将重挂」→ 确认。
- 语义：保留目标 `id`，源节点的所有边改挂到目标（重挂后成自环的边丢弃），源 `notes` 追加到目标 `notes`，源标题追加到目标 `aliases[]`（`entity` 没有 `aliases`，追加进 `notes`），最后删源节点；可撤销（§7.4）。
- 为什么不多给：两个问题、两个场景是不是同一个，要靠证据判断，自动建议会诱导人把不同问题合成一个；概念与实体是「同义不同名」的高发区，收益最大、代价最小。不做事前检查、只做事后合并：检查在编辑中途弹是噪音，合并是一次可预览可撤销的动作。

## §8 导出与实例化

导出要回答的是「给谁、拿去干什么、什么样算成功」，不是「能存成几种格式」。三种候选语义：

| 维度 | A 文档型 | B 结构型 | C 实例型 |
| --- | --- | --- | --- |
| 目标用户 | 人（评审、交给别人接着问）+ 别的工具（读 JSON） | 拿到模型就要建表或写类型的工程师 | 拿到模型就要开工的后端/前端 |
| 产物形态 | Markdown 说明书 + JSON 工作区 + 当前画布 SVG（PNG 降级） | TypeScript 接口骨架（另一种是 SQL DDL 或 JSON Schema） | 可编译的种子数据 + 校验/方法签名 |
| 生成规则（元素 → 产物的哪一行） | 问题 → 一行「P1 标题 · 状态」+ 陈述/判定标准/正反例；实体 → 一张字段表；`supportsQuestion` → 支撑关系一行 | `entity` → 一个 `interface`；`fields[]` → 属性；`states[]` → 联合类型；`identity` → 主键注释；`entityRelation` → 由 target 名派生的外键字段；行为与约束 → 注释 | `entity` → 每个实体固定 3 条样例实例；`constraint` → `export function 名称(x: 实体): boolean`；`behavior` → 方法签名 |
| 失败/降级 | 几乎不失败：缺什么少一行，文件头列「未完成项」 | `identity` 空 → 该实体整块注释掉并警告；未知字段类型 → `unknown` + 行尾注；`fields[]` 空 → 空接口 | 同 B；`expr` 是自由文本，**不转译成真实校验逻辑**，只给签名和 3 条样例 |

**推荐**：A 一定有；B **只做 TypeScript 类型骨架**（SQL DDL 与 JSON Schema 等有人真要了再谈）；C 作为 B 的附赠，固定每个实体 3 条样例实例。补一条理由：TypeScript 是唯一「零依赖就能验」的产物——`tsc --noEmit` 即验收；DDL 要数据库、JSON Schema 要校验器，本产品都不依赖。

### 8.1 A 的具体产物（保留已有三项，不扩）

- **Markdown 说明书**：一个文件两节——问题结构（树 + 每问题的 `status`/`statement`/`criteria[]`/正反例）与领域模型（实体字段与 `states[]`、行为、约束、`supportsQuestion` 支撑关系）；只用标题与列表标记。
- **JSON 工作区**：原样序列化 §4 信封（含 `schemaVersion`），可再导入；载入时版本更高则拒绝并给中文原因。
- **当前画布 SVG（PNG 降级）**：只导画布可见内容，不带顶栏与右栏。

### 8.2 完整性门槛（结论：不设硬门槛，只写文件头）

§5 的检查一条都不阻断编辑，也就不阻断导出——孤儿实体、未澄清问题、悬空引用**都能导**。代价是必须自曝：A、B、C 的文件头各有一段「未完成项」，逐条列「未支撑实体 N 个（C6）· 未澄清问题 N 个（C5）· 引用了已不存在规则 N 处（C5）」，为 0 写「无」。

唯一拒绝导出：schema 不合法（悬空边、端点类型不合法）。本产品写入即校验、载入即拒绝，正常路径上导不出这种文件；导出前仍跑同一条校验，失败则整包不导出并给中文原因。

### 8.3 导出验收（可判定，6 条）

1. TS 包放进空目录，`tsc --noEmit --strict` 退出码为 0。
2. `interface` 个数 = 工作区 `entity` 个数；每个接口上方注释为 `// 支撑：<问题 id> <问题标题>`，未支撑写 `// 支撑：无（C6）`。
3. 每个实体恰好 3 条样例实例，第 3 条必须违反该实体的至少一条 `constraint`，旁边写 `// 期望：拒绝`。
4. Markdown 里出现的问题 id 集合 = JSON 里 `question` 的 id 集合；同一工作区连导两次产物逐字节一致（幂等）。
5. 文件头「未完成项」段存在，无问题写「无」。
6. A/B/C 都不含 `pos`、选中态、缩放等 UI 状态（JSON 保留 `pos`，以支持原样再导入）。

## §9 明确砍掉了什么

1. v1 的 15 条边 → 留 11 条：`sharesState`/`conflictsWith`/`alternativeOf` 三条问题间边属于「同一问题域的视角切换」，画出来也没人维护。
2. v1 的 9 条检查 → 留 6 条：删掉的三条要么是 schema 硬校验（放在载入时），要么要靠人判断，做成自动提示只会制造噪音。
3. v1 的 5 个视图全塞在问题域 → 问题域 1 个、解域 1 个：视图一多，人不知道该在哪干活。
4. `example` 示例节点 → 降为问题的「正例/反例」文本：例子离开具体问题就没有意义，不值得占一个节点类型。
5. `note` 备注节点 → 降为任意节点的 `notes` 字段：备注是注释，不是结构。
6. `state` 节点 → `entity.data.states[]` 字符串数组：状态是实体的一个属性，独立成节点会诱人画出「状态图」。
7. v1 §12 与 `07-domain-mapping.md` 的 17 条升级规则与字段对照：版本已换，对照表只能误导实现者。
8. v1 的 8 类输出物 → 3 项导出：其余（剪贴板大纲、zip、报告页等）没有独立使用场景。
9. v1 的 8 条引导文案 → 全部砍掉：改为检查文案 + 空状态各一句，靠界面位置提示，不弹浮层。
10. v1 的 10 步核心流程 → 不再作为产品结构：步数写成文档骨架，实现时无人对照。
11. v1 的 schema 校验不变量 I1–I8 → 并入载入校验一句话（端点类型合法、无悬空边），不再单列。
12. v1 的 300 行完整样例 → 40 行以内样例：文档示例只证明结构，不承担验收。
13. 左栏问题导航 + 右栏检查 + 三栏常驻的强约束 → 只保留「右栏常驻」（§1）：其余留给 UI 稿定，产品稿不再复述布局。

## §10 不做什么

- 不做思维导图：没有无类型节点，新建节点必须选 9 类之一。
- 不做自由画板：画布上每条线都必须属于 11 类边之一，端点类型不合法直接拒绝。
- 不做全量 UML / 架构建模：解域只有实体、行为、约束，没有类图字段、没有时序/部署图。
- 不做多人协作与账号：本地存储单一来源，两个窗口同改以后写覆盖为已知行为。
- 不做 AI 自动生成或补全：所有节点与文案由人输入，没有模型调用。
- 不做流程/项目管理：没有负责人、工时、看板；状态只有问题澄清 5 态。
