# 07 · 问题域 → 领域模型：承接方法与判定规则

> 本文定义第 5 个视图「领域模型」的工作机制：前期产物（问题节点 + 领域元素节点 + 语义关系）如何被**判定**是否配升级为候选实体 / 值对象 / 关系 / 行为 / 约束，以及什么条件下允许进入该视图、什么条件下必须打回问题层。
>
> 定位：只做「建模承接」，不要求前期用 UML，不追求完整 DDD。所有判定必须可计算——本文不出现「取决于判断」。

## ASSUMPTIONS

编写本文时 `docs/design/01-product.md`（工作区 schema）尚未产出，以下字段与枚举为自拟。若 01-product.md 后续落地且命名不同，以其为准，本文公式只需换名、口径不变（对照见附录 A）。

### 节点类型（沿用产品大纲，不新增）

| 类型 | 枚举值 | 角色 | 关键字段 |
| --- | --- | --- | --- |
| 问题节点 | `question` | 第 1–4 步产物 | `id` `statement` `status`(`draft`/`clarifying`/`clarified`/`blocked`) `scope`(`in`/`out`/`undecided`) `importance`(`core`/`normal`/`minor`) |
| 参与者 | `participant` | 领域元素 | `boundary`(`internal`/`external`/`undecided`) `responsibility` |
| 场景 | `scenario` | 领域元素 | `steps[]` `pre` `post` `goal` |
| 领域概念 | `concept` | 领域元素 | `attributes[{name,type,required}]` `identity_candidates[]` `definition` |
| 领域规则 | `rule` | 领域元素 | `modality`(`always`/`conditional`) `expr` `target_refs[]` |
| 事件 | `event` | 领域元素 | `trigger` `changed_attrs[{concept,attr,from,to,op}]` `actor_ref` |
| 示例 | `example` | 领域元素 | `narrative` `refs[]` |

### 语义关系（边类型，含方向）

| 边 | 方向 | 含义 |
| --- | --- | --- |
| `references` | 问题 → 任意元素 | 该元素回答了该问题（**覆盖关系的唯一来源**） |
| `involves` | 场景 → 参与者/概念/事件 | 场景涉及 |
| `constrains` | 规则 → 概念 | 规则约束 |
| `affects` | 事件 → 概念 | 事件改变该概念状态 |
| `relates` | 概念 ↔ 概念 | 关联，带 `cardinality`(`1-1`/`1-N`/`N-M`/`aggregation`/`composition`) |
| `exemplifies` | 示例 → 问题/概念/规则 | 示例佐证 |
| `conflictsWith` | 规则 ↔ 规则 | 规则冲突，带 `status`(`open`/`resolved`) |
| `decomposes` | 问题 → 问题 | 子问题 |
| `serves` | 候选模型元素 → 问题 | 建模视图回指（新增，见 §5） |

### 候选模型元素（第 5 视图产出，不是前期节点）

`candidate_entity` `candidate_value_object` `candidate_relation` `candidate_behavior` `candidate_constraint` `candidate_usecase` `candidate_app_service` `state_transition` `state_machine`。
公共字段：`id` `name` `kind` `tier`(`A` 确定 / `B` 待定) `evidence_question_ids[]` `evidence_rule_ids[]` `evidence_event_ids[]` `status`(`proposed`/`promoted`/`demoted`)。

### 计数记号

- `#(X)`：集合基数，按 id 去重。
- `q`：`status=clarified` 且 `scope=in` 的问题节点；`Q` 为其集合。
- `边(src -[type]-> dst)`；双向边按一次计。
- 所有阈值是**默认值**，工作区可在配置里覆盖，但必须显式落库，不允许隐式「看情况」。

## 0. 视图职责与不变量

### 0.1 输入 / 输出契约

| 项 | 内容 |
| --- | --- |
| 输入 | 前 4 步的问题节点、领域元素节点、语义关系、清单与检查项结果 |
| 输出 | 候选模型元素 + 证据链（回指问题 / 规则 / 事件）+ 未覆盖清单 + 未决假设清单 |
| 不产生 | 新的事实。视图内**不允许**新增问题或领域元素；缺料只能打回问题层补 |
| 数据 | 与问题视图共用同一份状态，本视图是派生投影：`domainView = project(state, 'domain')`，只读 |

### 0.2 对抗两个失败模式

| 失败模式 | 对抗机制 | 落地章节 |
| --- | --- | --- |
| 问题分析未收敛就硬建模（把假设当实体） | 收敛闸门（硬性）+ `tier=A/B` 分级 + 未决假设清单必须随视图一起呈现 | §6、§7 |
| 视图变摆设（只换个布局再看一遍） | 本视图**必须**新增信息量：差分推出状态迁移草图、覆盖缺口清单、约束判定式；无新增信息量时视图拒绝渲染并给提示 | §3、§5、§7 |

### 0.3 三条硬不变量

1. **证据不变量**：任何 `status=promoted` 的候选元素，`evidence_question_ids ∪ evidence_rule_ids ∪ evidence_event_ids` 非空。
2. **单向不变量**：视图不能改问题层任何字段；打回只能由用户在问题层执行。
3. **可回指不变量**：每个候选元素必须能一键定位到至少 1 个问题（§7.3）。

## 1. 升级规则表（核心）

前提列中的 `∧` 为合取，全部满足才升级；任一不满足即停在元素层。信号编号见 §2。

### 1.1 领域概念 → 候选实体

| 编号 | 目标 | 升级前提（可计算） | 反例（不许升级） | 降级条件（打回问题层） |
| --- | --- | --- | --- | --- |
| U-E1 | `candidate_entity`（tier A） | `S01 qref≥2` ∧ `S02 attr≥2` ∧ `S08 identity≥1` ∧ `S09 changable=1` | 仅 1 个属性且无边（如「金额」）；只在一句话里出现；名字等于某个 UI 输入框名 | 引用它的问题被重开为 `clarifying`；或 2 轮迭代内 `attr` 未增且 `qref` 下降 → 退回元素层 |
| U-E2 | `candidate_entity`（tier B） | `S01 qref≥2` ∧ `S02 attr≥2` ∧ `S08 identity≥1` ∧ `S09=0` | 同上；另：`S11` 命中（单属性零关联）不许进 B | 生命周期问题补不出答案时转 `candidate_value_object` 重判；问题重开则打回 |

### 1.2 领域概念 → 候选值对象

| 编号 | 目标 | 升级前提（可计算） | 反例（不许升级） | 降级条件（打回问题层） |
| --- | --- | --- | --- | --- |
| U-V1 | `candidate_value_object` | `S01 qref≥2` ∧ `S02 attr≥2` ∧ `S08 identity=0` ∧ `S09=0` | 有身份标识；存在以它为主语的更新事件 | 出现「同值但需区分批次」需求 → 打回概念层重判是否为实体 |
| U-V2 | `candidate_value_object` | `S01 qref≥2` ∧ `S02 attr≥1` ∧ `S10 shared≥1` ∧ `S08=0` ∧ `S09=0` | 被 1-N 关系当作「拥有者」引用（应为主体实体） | 共享关系被删除 → 退回属性层 |
| U-V3 | `candidate_value_object` | 作为复合属性出现在 ≥2 个候选实体的 `attributes` 上 | 只出现在 1 个实体的 1 个属性上（不值得建类型） | 复用度降到 1 → 合并回属性 |

### 1.3 领域规则 → 业务约束 / 不变量

| 编号 | 目标 | 升级前提（可计算） | 反例（不许升级） | 降级条件（打回问题层） |
| --- | --- | --- | --- | --- |
| U-R1 | `candidate_constraint`（业务约束） | `S13 rq≥1` ∧ `S14 conflict=0` ∧ `S15 target≥1` ∧ `S18 实现泄漏=0` | `conflict>0`；`target=∅`（「系统要快」）；`expr` 含表名/接口名/字段路径 | 规则引用的问题被重开；或判定为另一条规则的推论（冗余）→ 合并后退回 |
| U-R2 | `candidate_constraint`（可判定式） | U-R1 成立 ∧ `S16 checkable=1` ∧ 全部 `target` 已是候选实体/值对象 | `expr` 无法落到比较符/枚举域/算术（如「尽量」「合理」） | 目标元素被打回 → 判定式一起失效，退回 |
| U-I1 | `candidate_constraint`（不变量） | U-R1 成立 ∧ `S17 modality=always` ∧ 单实体/单聚合内闭合 | `modality=conditional`（只在某前置条件下成立，属业务约束）；跨 2 个以上聚合 | 缺事务边界信息 → 降为「待定约束」进未决清单，不改问题层 |
| U-I2 | `candidate_constraint`（不变量） | `S17=always` ∧ 该约束被 ≥1 个状态迁移的前后置条件引用（§3 产出） | 只在某个事件里检查一次（那是行为的前置条件） | 状态机被打回 → 挂回业务约束 |

### 1.4 事件 → 领域事件 / 状态迁移

| 编号 | 目标 | 升级前提（可计算） | 反例（不许升级） | 降级条件（打回问题层） |
| --- | --- | --- | --- | --- |
| U-DE1 | `candidate_behavior`（领域事件） | `S19 sc≥1` ∧ `S21 actor=1` ∧ (`S20 Δ≥1` ∨ 有下游消费者) ∧ `S22 crud=0` | 事件名为「保存/更新/查询/删除」；无状态差且无消费者（纯技术事件） | 所属场景被判 `scope=out` → 移出视图 |
| U-DE2 | `candidate_behavior`（强证据） | U-DE1 成立 ∧ `S23 ex≥1` ∧ (`S13` 类规则引用 ≥1) | 只在示例里出现、无任何场景涉及（是背景不是事件） | 示例被删或场景重开 → 降为 tier B |
| U-ST1 | `state_transition` | `S20 Δ(c)≥1` ∧ `c` 已是候选实体 ∧ `changed_attrs` 的 `from`/`to` 可枚举或有序 | 变更的是审计字段（`updated_at`）或派生字段（`total=sum(items)`） | 值域无法枚举（自由文本）→ 打回问题层补示例 |
| U-ST2 | `state_machine` | 同一概念上 `#(transitions)≥2` 且共享 ≥2 个状态值 | 只有 1 条迁移（是行为不是状态机） | 迁移被打回后剩 <2 条 → 状态机解散为迁移列表 |

### 1.5 参与者 → 角色 / 外部系统

| 编号 | 目标 | 升级前提（可计算） | 反例（不许升级） | 降级条件（打回问题层） |
| --- | --- | --- | --- | --- |
| U-RO1 | `candidate_entity`（角色，tier A） | `S24 scen≥1` ∧ `S26 boundary=internal` ∧ `S25 resp≠∅` | 泛称「用户」「系统」，无责任描述；一人承担 >5 个场景仍无职责划分（先拆） | 其涉及场景全部 `scope=out` → 移出 |
| U-XS1 | `candidate_entity`（外部系统，tier A） | `S24 scen≥1` ∧ `S26 boundary=external` ∧ (该参与者是某事件 `actor` ∨ 是某规则 `target`) | 内部模块被标 `external`（边界未澄清）；`boundary=undecided` | 边界问题重开 → 打回边界澄清步骤 |

### 1.6 场景 → 用例 / 应用服务候选

| 编号 | 目标 | 升级前提（可计算） | 反例（不许升级） | 降级条件（打回问题层） |
| --- | --- | --- | --- | --- |
| U-UC1 | `candidate_usecase` | `S27 steps≥2` ∧ `S28 pre/post 非空` ∧ `S29 actors≥1` ∧ 场景被 ≥1 个 `clarified` 问题引用 | 一句话目标（`steps<2`）；一个场景装 2 个不相关目标（先拆场景） | 对应核心问题被重开 → 用例打回 |
| U-AS1 | `candidate_app_service` | U-UC1 成立 ∧ `S30 span≥2`（跨 ≥2 个候选实体） ∧ 需事务/编排（示例中存在跨实体顺序约束） | 单实体内部行为（归实体行为）；`S31 readonly=1`（纯查询，不建应用服务） | 应用服务数 > 用例数×1.5 或 1:1 → 提示过度分层，退回 |

**合计 17 条升级规则**，覆盖 5 类源 → 8 类目标。规则若与 §2 信号冲突，以信号的实际计数为准（规则只表达组合方式）。

## 2. 判定信号清单

每条信号都可直接算数。`Q` = `clarified ∧ scope=in` 的问题集合；`S` = 场景集合；`E` = 事件集合；`R` = 规则集合；`C` = 概念集合；`P` = 参与者集合。

| ID | 信号名 | 适用 | 计算公式 | 阈值 | 不足时提示文案 |
| --- | --- | --- | --- | --- | --- |
| S01 | 概念问题支撑数 | 概念 | `qref(c) = #({q ∈ Q : q -[references]-> c})` | ≥2 | 「『{name}』只被 {n} 个已澄清问题引用，先回到问题层补一个它会回答的问题，再回来建模」 |
| S02 | 概念属性数 | 概念 | `attr(c) = #(dedupe(c.attributes, by=name))` | ≥2 | 「『{name}』只有 {n} 个属性，还看不出结构：补属性，或确认它其实是一个属性而非概念」 |
| S03 | 概念关联度 | 概念 | `deg(c) = #({x ∈ C∪P : c -[relates]-> x})` | ≥2 | 「『{name}』与其它概念没有关系边，孤立概念不建模：先建立它和 {候选} 的关系」 |
| S04 | 概念跨场景度 | 概念 | `scen(c) = #({s ∈ S : s -[involves]-> c})` | ≥2 | 「『{name}』只在 1 个场景出现，可能只是该场景的局部细节，不建议升级」 |
| S05 | 概念被约束数 | 概念 | `ruler(c) = #({r ∈ R : r -[constrains]-> c})` | ≥1 | 「『{name}』没有任何规则约束，先问：什么情况下它是不合法的？」 |
| S06 | 概念被事件改变数 | 概念 | `mod(c) = #({e ∈ E : e -[affects]-> c ∧ changed_attrs≠∅})` | ≥1 | 「没有事件改变『{name}』，它是静态数据还是根本没被想清楚？」 |
| S07 | 概念示例支撑数 | 概念 | `ex(c) = #({p : p -[exemplifies]-> c})` | ≥1 | 「『{name}』缺少具体例子，补一个真实数据样例再升级」 |
| S08 | 身份线索数 | 概念 | `identity(c) = #(c.identity_candidates)` | ≥1（实体） / =0（值对象） | 「『{name}』没有身份标识线索：两个它，怎么判断是不是同一个？」 |
| S09 | 就地可变性 | 概念 | `changable(c) = 1` 当且仅当 `∃e ∈ E: e.changed_attrs` 中存在 `op=update` 且 `concept=c` | =1（实体） / =0（值对象） | 「『{name}』没有被就地修改的证据，倾向值对象；若确实会变，补一个改变它的事件」 |
| S10 | 被共享度 | 概念 | `shared(c) = #({z : z -[relates,cardinality∈{1-N,N-M,aggregation}]-> c})` | ≥1 | 「『{name}』没有被多个实例共享的迹象，可能只是属性而非独立类型」 |
| S11 | 属性级抑制（负向） | 概念 | `attr(c)=1 ∧ deg(c)=0` | 命中即抑制 | 「『{name}』是单属性零关联，暂按属性处理：不建实体/值对象」 |
| S12 | UI 字段泄漏（负向） | 概念 | `name(c) ∈ ui_labels(state) ∨ 存在 references 边来自 UI 字段问题` | 命中即抑制 | 「『{name}』看起来是界面上的一个输入框名，不是领域概念：换用业务语言重命名」 |
| S13 | 规则问题支撑数 | 规则 | `rq(r) = #({q ∈ Q : q -[references]-> r})` | ≥1 | 「『{name}』没有回答任何已澄清问题，可能是想当然的规则」 |
| S14 | 规则冲突数 | 规则 | `conflict(r) = #({r' : r -[conflictsWith]-> r' ∧ r'.status=open})` | =0 | 「『{name}』与 {r'} 冲突且未裁决，冲突未解决前不许升级；先在问题层裁决」 |
| S15 | 规则约束对象数 | 规则 | `target(r) = #(r.target_refs)` | ≥1 | 「『{name}』没有约束对象：它约束的是什么的什么？补上目标概念」 |
| S16 | 可判定性 | 规则 | `checkable(r) = 1` 当 `expr` 命中（比较符／枚举域／算术式）且 `target≠∅` | =1（不变量/判定式） | 「『{name}』无法判定真假：改成「{属性} {比较符} {阈值}」的写法」 |
| S17 | 模态 | 规则 | `modality(r) ∈ {always, conditional}` | `always`（不变量） | 「『{name}』只在特定条件下成立，归为业务约束而非不变量」 |
| S18 | 实现泄漏（负向） | 规则 | `implementation_leak(r) = 1` 当 `expr` 命中（表名/接口名/字段路径/框架词） | =0 | 「『{name}』写成了实现条件，改成业务语言：约束的是业务事实，不是代码」 |
| S19 | 事件场景涉及数 | 事件 | `sc(e) = #({s ∈ S : s -[involves]-> e})` | ≥1 | 「『{name}』不属于任何场景，它真的会发生吗？」 |
| S20 | 状态差 | 事件 | `Δ(e) = #(e.changed_attrs)`（仅计 `op∈{update,transition,delete,create}` 且非派生/审计字段） | ≥1 | 「『{name}』没有改变任何概念状态，它是通知还是事件？」 |
| S21 | 触发者明确性 | 事件 | `actor(e) = 1` 当 `e.actor_ref` 非空（参与者或定时/外部触发） | =1 | 「『{name}』没说谁触发，补触发者（人/系统/时间）」 |
| S22 | CRUD 名（负向） | 事件 | `crud(e) = 1` 当 `name` 命中（保存/更新/删除/查询/新增/modify/save/update） | =0 | 「『{name}』是技术动作不是领域事件，换成业务语言：如「选课提交」「容量占满」」 |
| S23 | 事件示例支撑 | 事件 | `ex(e) = #({p : p -[exemplifies]-> e})` | ≥1 | 「『{name}』没有实例，补一个真实发生过的例子」 |
| S24 | 参与者场景数 | 参与者 | `scen(p) = #({s ∈ S : s -[involves]-> p})` | ≥1 | 「『{name}』不参与任何场景，它是否在范围外？」 |
| S25 | 责任描述 | 参与者 | `resp(p) = len(trim(p.responsibility)) > 0` | 非空 | 「『{name}』没有责任描述，用一句话写：它负责做什么决定/动作」 |
| S26 | 边界归属 | 参与者 | `boundary(p) ∈ {internal, external}` | 已决 | 「『{name}』未判定在系统边界内还是外，先回到边界澄清」 |
| S27 | 场景步骤数 | 场景 | `steps(s) = #(s.steps)` | ≥2 | 「『{name}』只有 {n} 步，可能是一句话目标而非场景」 |
| S28 | 前后置完整性 | 场景 | `pre(s)≠空 ∧ post(s)≠空` | 两者非空 | 「『{name}』缺少前置或后置条件，补：开始前为真、结束后为真」 |
| S29 | 场景参与者数 | 场景 | `actors(s) = #({p : s -[involves]-> p})` | ≥1 | 「『{name}』没有参与者，谁在推动这件事？」 |
| S30 | 跨实体跨度 | 场景 | `span(s) = #({ce : ce.kind∈{candidate_entity,candidate_value_object} ∧ ce 参与 s})` | ≥2（应用服务） | 「『{name}』只在一个实体内部，属实体行为，不建应用服务」 |
| S31 | 纯查询（负向） | 场景 | `readonly(s) = 1` 当 `s` 的所有 `changed_attrs=∅` | 命中则不做 AS | 「『{name}』只读不写，属查询候选，不建应用服务」 |

**共 31 条信号**（含 5 条负向抑制信号 S11/S12/S18/S22/S31），每条均给出计数公式与阈值。

### 2.1 计算口径约定

1. **去重**：同一概念被 3 个问题引用计 3；同一问题引用同一概念两次计 1。
2. **边方向**：只按表中方向计；反向边不计入该信号。
3. **澄清过滤**：`Q` 只含 `clarified ∧ in`；`draft`/`clarifying`/`blocked` 的问题不计入任何信号（这是防「假设当实体」的第一道闸）。
4. **派生字段排除**：`changed_attrs` 中 `attr` 为 `total`/`count`/`updated_at` 等派生或审计字段时，`S20` 不计。
5. **实现**：信号以纯函数 `signal(state, nodeId) → {value, threshold, ok}` 形式暴露，视图与导出共用同一实现，禁止两处各算一套。

## 3. 状态迁移提取

### 3.1 差分步骤（对每个事件 `e` 执行）

1. 取 `C(e) = {c : e -[affects]-> c}`；为空则 `S20=0`，事件停在 `candidate_behavior` 层，不产迁移。
2. 对每个 `c ∈ C(e)`，取 `A(e,c) = {a ∈ e.changed_attrs : a.concept=c ∧ 非派生/审计}`。
3. 把 `(c, A)` 映射到状态字段：若某属性 `a` 的 `to` 取值域可枚举（≤8 个值）→ 该属性即状态字段；若有序数值 → 取区间边界为状态。
4. 生成迁移边 `t = (c.state_field, a.from, a.to, label=e.name, pre=e.pre, post=e.post)`；`from` 缺失时标 `?`（初始态待定），并进未决假设清单。
5. 同一概念上合并 `t`：相同 `(from,to)` 只保留 1 条，`label` 用「/」连接。
6. 体检：输出 `状态数`、`迁移数`、`无入边状态`、`无出边终态`、`不可达状态`；任一异常 → 该状态机 `tier=B` 并给提示。

## 4. 实体 vs 值对象判定

### 4.1 判定流程（按顺序，第一个命中即定）

```
输入 概念 c
  │
  ├─ S11 命中（attr=1 ∧ deg=0）──────────────→ 不升级，按"属性"处理
  │
  ├─ Q1 有身份？ identity(c) ≥ 1
  │    否 ──→ Q2
  │    是 ──→ Q2' 会就地变？ S09=1
  │            是 ──→ 【候选实体】(tier A)
  │            否 ──→ Q3' 被共享（S10≥1）且需按身份追踪历史？
  │                     是 ──→ 【候选实体】tier B（生命周期待定）
  │                     否 ──→ 【候选实体】tier B（弱）
  │
  └─ Q2 会就地变？ S09=1
       是 ──→ 【候选实体】(身份待定，tier B，必须在未决清单说明"还没有身份标识")
       否 ──→ Q3 被共享？ S10 ≥ 1
              是 ──→ Q4 可替换？ 用相等属性集合替换任一实例后，系统行为不变
                       是 ──→ 【候选值对象】
                       否 ──→ 【候选实体】tier B（共享且有独立生命周期）
              否 ──→ Q4 可替换？
                       是 ──→ 【候选值对象】（可内联为属性，视复用度）
                       否 ──→ 停在概念层：既非实体也非值对象，标注"建模缺口"
```

**四个问题对应的可计算口径**

| 问题 | 判据 | 信号 |
| --- | --- | --- |
| 有身份？ | `identity_candidates` 非空，或存在「两个实例必须区分」的规则/示例 | S08 |
| 会变？ | 存在 `op=update` 事件以它为主语 | S09 |
| 被共享？ | 在 `1-N`/`N-M`/`aggregation` 关系里被引用 | S10 |
| 可替换？ | `S08=0 ∧ S09=0`，且示例中替换后行为不变（示例里没有「跟踪它的变化」叙事） | S08 ∧ S09 ∧ S07 |

### 4.2 三个概念走通（选课样例）

| 概念 | 有身份 | 会变 | 被共享 | 可替换 | 判定 | 依据 |
| --- | --- | --- | --- | --- | --- | --- |
| 学生 | 是（学号，`identity_candidates=[学号]`） | 是（E「学籍异动」改 `status`） | 是（`选课记录 -[relates,N-M]-> 学生`） | 否 | **候选实体**（tier A） | S08=1 ∧ S09=1；`U-E1` 全满足；`S01` 从 S1/S2 两问题得 2 |
| 课程班次 | 是（班次号 / 学期+课程+序号） | 是（`enrolled`、`capacity_state` 被 E1/E4/E5 改变） | 是（`课程 -[relates,1-N]-> 课程班次`） | 否 | **候选实体**（tier A） | S08=1 ∧ S09=1；承载不变量 R1（`S05=1`）；`U-ST1` 产出容量状态机 |
| 时间区间 | 否（无 identity 线索） | 否（示例中从不修改，只整体替换） | 是（出现在课程班次与选课记录两处，`S10=1`） | 是（换成另一个等值区间，行为不变） | **候选值对象** | S08=0 ∧ S09=0 ∧ S10=1 ∧ S02=2（`start`,`end`）→ `U-V2` |
| 选课记录（附） | 是（学生+班次唯一，或流水号） | 是（`status` 迁移） | 是（被教务审核场景引用） | 否 | **候选实体**（tier A） | 状态机主语；`U-ST2` 产出 4 状态 |

**反例说明（写进卡片提示）**：若把「时间区间」建成实体，则每次改时间都会留下版本历史——但示例中从未出现「同一时间区间被改后仍要认得是它」的叙事，故为值对象；若把「学生」建成值对象，则退课时无法定位同一学生，与 R2 冲突。

## 5. 问题覆盖 ↔ 模型覆盖双向核对

### 5.1 正向：每个已澄清问题都被至少一个模型元素解释

定义「被解释」：存在候选模型元素 `m`，满足 `m.evidence_question_ids ∋ q` 且 `m` 的元素类型与 `q` 的期望类型匹配（映射表见下）。

| 问题类型（按 `q.tags` 或句式判定） | 可解释它的模型元素 |
| --- | --- |
| 规则类（含「不得/必须/最多/至少」） | `candidate_constraint` |
| 状态/流程类（含「之后/当…时/变化」） | `candidate_behavior`、`state_machine` |
| 结构类（含「包括/由…组成/有哪些」） | `candidate_entity`、`candidate_value_object`、`candidate_relation` |
| 交互类（含「谁/如何操作」） | `candidate_usecase`、`candidate_app_service` |

```
function forwardCoverage(state):
    uncovered = []
    for q in sort(Q, by=[-importance, id]):          # 稳定排序，输出可复现
        ok = exists(m in CANDIDATES:
                    q.id in m.evidence_question_ids
                    and kind(m) in allowedKinds(q))
        if not ok: uncovered.append(q.id)
    return uncovered
```

### 5.2 反向：每个候选实体都服务于至少一个问题

`serves(ce, q)` 成立当且仅当 `q.id ∈ ce.evidence_question_ids` 且 `q ∈ Q`。孤儿清单：

```
function reverseCoverage(state):
    orphans = []
    for ce in sort(CANDIDATES, by=id):
        if ce.kind in {candidate_entity, candidate_value_object, candidate_relation,
                       candidate_behavior, candidate_constraint}:
            served = [q for q in ce.evidence_question_ids if q in Q]
            if served == []: orphans.append(ce.id)
    return orphans
```

### 5.3 文案（直接可用的界面字符串）

| 场景 | 文案 |
| --- | --- |
| 正向缺口 | 「{n} 个已澄清问题还没有任何模型元素解释：{Q-003、Q-007}。它们要么缺一个候选实体/约束，要么当初澄清得不够——回问题视图看一眼再决定。」 |
| 反向孤儿 | 「{n} 个候选元素找不到它回答的问题：{CE-02『时间区间』}。删掉它，或回到问题层补一个它服务的问题。」 |
| 双向通过 | 「覆盖核对通过：{a}/{a} 个已澄清问题被解释，{b}/{b} 个候选元素有归属问题。」 |
| 双向都有缺口（优先处理） | 「先补反向：孤儿元素 {ids} 说明模型比问题多；补完再处理正向缺口 {ids}。」 |

**判定优先级**：反向孤儿优先于正向缺口——孤儿意味着「凭空造模型」，正是失败模式一。

## 6. 收敛判定：什么时候可以进入建模视图

### 6.1 硬性闸门（任一不满足即拒绝渲染建模内容，只显示闸门清单）

| 编号 | 闸门 | 判定式 | 阈值 | 提示文案 |
| --- | --- | --- | --- | --- |
| G1 | 核心问题已澄清 | `#({q ∈ Q_core, scope=in, status=clarified}) / #({q ∈ Q_core, scope=in})` | = 100% | 「还有 {n} 个核心问题没澄清（{ids}），现在建模会把假设当实体。」 |
| G2 | 总体澄清率 | 同上，分母为全部 `scope=in` 问题 | ≥ 80% | 「范围内问题澄清率 {p}%，低于 80%：先收敛再建模。」 |
| G3 | 无阻断级检查项 | `blockers = #({检查项 : severity=blocker ∧ 未解决})` | = 0 | 「有 {n} 个阻断项未解决：{项名}。」 |
| G4 | 范围非空 | `#({q : scope=in})` | ≥ 3 | 「范围内问题不足 3 个，范围还没划出来。」 |
| G5 | 领域元素非空且足型 | `#(E) ≥ 5` ∧ `#({type : E})` | ≥5 个、≥3 种类型 | 「领域元素只有 {n} 个 / {k} 种类型，材料不足以抽象。」 |
| G6 | 存在反例示例 | `#({p : type=example}) ≥ 1` ∧ 该示例被 ≥1 问题 `-[exemplifies]->` | ≥1 | 「还没有任何真实例子：抽象前至少给一个具体案例（含反例）。」 |
| G7 | 概念有支撑 | `#({c : S01(qref)≥2})` | ≥ 3 | 「只有 {n} 个概念被 ≥2 个问题引用，模型会很薄。」 |
| G8 | 无未裁决冲突 | `#({r : S14(conflict)>0})` | = 0 | 「规则 {r1} 与 {r2} 冲突未裁决，先裁决再建模。」 |

### 6.2 软性建议（不阻断，进入视图后以横幅呈现）

| 编号 | 建议 | 判定式 | 阈值 | 提示文案 |
| --- | --- | --- | --- | --- |
| G9 | 概念平均支撑度 | `Σ qref(c) / #(C)` | ≥ 1.5 | 「平均每个概念只被 {x} 个问题引用，模型可能偏薄。」 |
| G10 | 核心场景有事件 | `#({s ∈ S_core : ∃e, s -[involves]-> e}) / #(S_core)` | ≥ 80% | 「{n} 个核心场景没有对应事件，状态迁移会缺边。」 |
| G11 | 未决假设可控 | `#(未决假设) / #(C)` | ≤ 0.3 | 「未决假设 {n} 条，超过概念数的 30%，考虑先补澄清。」 |
| G12 | 覆盖缺口 | §5 正向缺口 + 反向孤儿 | 建议 = 0 | 「覆盖缺口：正向 {n}、反向 {m}，不影响建模但要在未决清单里可见。」 |

**共 12 条闸门**（8 硬 + 4 软）。闸门判定结果落库为 `convergence_report`，随导出文档一起生成，便于复核「当时凭什么允许建模」。

| `判定式` | `enrolled <= capacity` |
| `来源规则` | `R-001` |
| `证据(问题)` | `Q-016` |
| `状态` | 同 8.1 |

### 8.5 证据标注规则

1. 每个候选元素至少 1 个证据单元；证据单元格式 `Q-nnn` / `R-nnn` / `E-nnn`，多个用 `、` 连接，**不写自由文本**（自由文本进 `备注`，不参与核对）。
2. 证据必须指向 `clarified` 问题；指向 `draft`/`clarifying` 问题时导出前置校验失败并列出清单。
3. 无证据的行导出为 `—` 并在文末「无证据清单」列出，附「删除或补问题」的建议。
4. 导出前置校验：`孤儿清单=∅ ∧ 无证据行=∅ ∧ convergence_report 存在`；任一失败 → 导出被拒绝，提示具体清单（可强制导出，但文档头加「未通过校验」横幅）。
5. 导出文档头固定包含：生成时间、`convergence_report` 摘要（闸门通过数/失败项）、覆盖核对结果（§5.3 文案原文）。

## 10. 与 DDD 术语的对齐声明

### 10.1 选择：简化子集，不做完整 DDD

本工具采用 **Entity / ValueObject / Relation / Behavior / Constraint** 五个建模元素，**不**把 Aggregate、AggregateRoot、BoundedContext、Repository、Factory、DomainService 作为一等公民。

| 本工具术语 | DDD 对应 | 是否一等公民 | 理由 |
| --- | --- | --- | --- |
| 候选实体 | Entity | 是 | 由「有身份 + 会变」可判定，输入材料足够 |
| 候选值对象 | Value Object | 是 | 由「无身份 + 不可变 + 可替换」可判定 |
| 候选关系 | Association / 1-N / N-M | 是 | 前 4 步已有语义关系边，可直接承接 |
| 候选行为 | Domain Behavior / Method | 是 | 事件 + 前置后置即可表达 |
| 候选约束 | Invariant / Business Rule | 是 | 规则节点可判定性足够 |
| 聚合 | Aggregate | 否，降级为关系表的 `聚合/组合` 标注 | 聚合边界依赖一致性/事务知识，前期不可得；强行判定等于把假设升级成架构承诺 |
| 限界上下文 | Bounded Context | 否 | 本工具处理单个问题域，不做战略拆分 |
| 仓储 / 工厂 / 领域服务 | Repository / Factory / DomainService | 否 | 属实现层，超出「问题域 → 领域模型」的边界 |

### 10.2 理由

1. **输入语言不是 DDD 语言**：前 4 步产出的是业务语言（参与者、场景、概念、规则、事件、示例），直接映射到 DDD 战术模式会产生大量无法判定的空洞（如「这个聚合根是谁」）。
2. **用户不是架构师**：本工具面向产品/业务分析者，要求他们决定聚合边界会直接诱发失败模式 F5（假设当实体）。
3. **可判定性优先**：只保留能用计数与枚举判定的概念；凡是需要「架构经验判断」的 DDD 概念一律不进判定表，最多作为导出后的下游输入。
4. **反向兼容**：导出表的结构（实体/关系/行为/约束）可被下游 UML/DDD 工具消费；若团队后续要做聚合设计，聚合候选可由「组合关系 + 不变量归属」在导出后推导，不由本工具断言。

### 10.3 明确的术语边界

- 本工具的「实体」= 候选实体，不代表最终领域模型结论，`tier=B` 时必须带未决假设。
- 本工具的「不变量」只表示「任何时刻都应成立且可判定」的约束，不含跨聚合最终一致性语义。
- 本工具不输出 `Aggregate` 一词，避免用户误以为已完成战术设计。
